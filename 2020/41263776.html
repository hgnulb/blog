    synchronized 是什么

    Java 平台中的任何一个对象都有唯一一个与之关联的锁，这种锁被称为监视器（monitor）或者内部锁。内部锁是一种排他锁：同一时刻最多只有一个线程能持有某个对象的监视器，其它来抢的线程只能阻塞等待。

    内部锁通过 synchronized 关键字使用，它能够同时保障原子性、可见性和有序性——这也是面试官问「synchronized 能解决什么问题」时的标准答案。被 synchronized 保护的代码区域称为临界区，进入临界区必须先拿到对应的监视器。

    理解 synchronized 的一切问题，只需要抓住一条主线：这段代码抢的是哪个对象的监视器。后文的三种用法、八锁问题，全部围绕这条主线展开。

    synchronized 的三种用法

    synchronized 可以修饰实例方法、静态方法和代码块，三种写法的唯一区别就是锁对象不同：

    用法 锁对象
    修饰实例方法 当前实例，即 this
    修饰静态方法 当前类的 Class 对象
    修饰代码块 括号里显式指定的对象

    修饰实例方法：锁 this

    synchronized 修饰的实例方法称为实例同步方法，整个方法体就是一个临界区，锁的是调用该方法的那个对象（this）。因此写成同步方法和用 synchronized (this) 包住方法体是完全等效的：

    synchronized void method() {
}

// 与上面的写法等效
void method() {
    synchronized (this) {
    }
}

    下面用两个线程并发对同一个对象自增来验证：increment() 锁的是 demo 这一把对象锁，i++ 这个「读-改-写」复合操作被互斥保护，结果恒为 200000；去掉 synchronized 则大概率小于 200000。

    public class InstanceLockDemo {
    private int count = 0;

    // 实例同步方法，锁的是调用它的对象 this
    public synchronized void increment() {
        count++;
    }

    public static void main(String[] args) throws InterruptedException {
        InstanceLockDemo demo = new InstanceLockDemo();
        Runnable task = () -> {
            for (int i = 0; i < 100000; i++) {
                demo.increment();
            }
        };
        Thread t1 = new Thread(task);
        Thread t2 = new Thread(task);
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        System.out.println("count = " + demo.count);
    }
}

    [!green-fold] 运行结果

    count = 200000

    修饰静态方法：锁 Class 对象

    synchronized 修饰的静态方法称为静态同步方法，锁的是该类的 Class 对象（如 Something.class）。Class 对象在 JVM 中每个类只有一份，所以这把锁常被叫作类锁——无论通过哪个实例、哪个线程去调用，抢的都是同一把锁。它与 synchronized (类名.class) 代码块等效。

    下面的例子里，两个线程分别包着两个不同的 Runnable 实例，但 increment() 是静态同步方法，锁的是 StaticLockDemo.class 这唯一一把类锁，结果依然恒为 200000。如果把 increment() 改成实例同步方法，两个实例两把锁，结果就会小于 200000——这是「对象锁 vs 类锁」最直观的对照实验。

    public class StaticLockDemo implements Runnable {
    private static int count = 0;

    // 静态同步方法，锁的是 StaticLockDemo.class 这把类锁
    public static synchronized void increment() {
        count++;
    }

    @Override
    public void run() {
        for (int i = 0; i < 100000; i++) {
            increment();
        }
    }

    public static void main(String[] args) throws InterruptedException {
        Thread t1 = new Thread(new StaticLockDemo());
        Thread t2 = new Thread(new StaticLockDemo());
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        System.out.println("count = " + count);
    }
}

    [!green-fold] 运行结果

    count = 200000

    修饰代码块：锁指定对象

    synchronized 修饰的代码块称为同步块，锁的是括号里显式指定的那个对象（锁句柄）。它比同步方法更灵活：既能缩小临界区范围（只锁真正需要互斥的几行），也能自由选择锁的粒度——锁 this、锁 Class 对象、或锁一个专门的私有对象都行。

    synchronized (锁句柄) {
}

    [!amber]
    注意： 作为锁句柄的变量通常采用 private final 修饰，如：private final Object lock = new Object(); 这样能防止锁对象被意外替换，也避免外部代码拿到这把锁造成干扰或死锁。

    下面的例子用一个专门的 lock 对象保护 count：两个线程抢的是同一把 lock 锁，结果恒为 200000。锁句柄换成任何两个线程共享的同一个对象都成立。

    public class BlockLockDemo {
    private static int count = 0;
    private static final Object lock = new Object();

    public static void main(String[] args) throws InterruptedException {
        Runnable task = () -> {
            for (int i = 0; i < 100000; i++) {
                // 同步块，锁的是显式指定的 lock 对象
                synchronized (lock) {
                    count++;
                }
            }
        };
        Thread t1 = new Thread(task);
        Thread t2 = new Thread(task);
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        System.out.println("count = " + count);
    }
}

    [!green-fold] 运行结果

    count = 200000

    最后再对比一下代码块的两种常见锁对象：

    // this 锁的是当前实例对象
synchronized (this) {
    for (int j = 0; j < 1000000; j++) {
        i++;
    }
}

// class 锁的是当前类的 Class 对象
synchronized (AccountingSync.class) {
    for (int j = 0; j < 1000000; j++) {
        i++;
    }
}

    synchronized 的特性

    • 原子性：临界区内的代码同一时刻只被一个线程执行，i++ 这类「读-改-写」复合操作不会被其它线程插队打断。

    • 可见性：线程释放锁时会把工作内存中的修改刷回主内存，另一个线程获取同一把锁时会重新从主内存读取，因此前一个线程在临界区内的写入对后一个线程可见（happens-before 中的监视器锁规则）。

    • 有序性：同一把锁的临界区之间是串行执行的，从获取同一把锁的线程视角看不到临界区内的指令重排效果。注意这不等于禁止重排序——临界区内部仍可能重排，这也是 DCL 单例还需要 volatile 的原因。

    • 可重入：一个线程试图获取其它线程持有的锁时会阻塞；但再次请求自己已持有的锁时会成功，这就是锁重入。因此一个线程在 synchronized 方法内部可以直接调用同一个对象的另一个 synchronized 方法，也可以在子类同步方法里调用父类的同步方法，不会把自己锁死。底层靠监视器中的计数器实现：重入一次加一，退出一次减一，减到零才真正释放。ReentrantLock 同样可重入（类名就叫「可重入锁」）。

    • 自动释放锁：同步代码执行结束或抛出异常时，JVM 都会自动释放监视器，不存在忘记解锁的问题；而 ReentrantLock 必须手动 unlock()，且必须放在 finally 里，漏写就是死锁隐患。

    • 不可中断：一个线程在阻塞等待 synchronized 锁的过程中不能响应中断，只能一直等下去；而 ReentrantLock 提供了可中断的 lockInterruptibly() 和可超时放弃的 tryLock(timeout)。

    • 非公平：锁释放时等待中的线程不按申请顺序获得锁，由 JVM 从竞争线程中挑选（新来的线程甚至可以直接插队抢到），且无法像 ReentrantLock 那样通过构造参数配置成公平锁。非公平的好处是吞吐量更高。

    synchronized 底层实现与锁升级

    底层实现

    • 同步代码块：编译后在进入处插入 monitorenter、退出处插入 monitorexit 字节码指令（异常路径上也有一条 monitorexit，保证异常时锁一定释放）。线程执行 monitorenter 时尝试获取对象关联的监视器（monitor）的所有权。

    • 同步方法：不使用这两条指令，而是在方法的访问标志中打上 ACC_SYNCHRONIZED 标记，JVM 调用该方法前隐式获取监视器，方法返回时释放。

    • 监视器的重量级实现（ObjectMonitor）依赖操作系统的互斥量（mutex），抢锁失败的线程要阻塞挂起，涉及用户态到内核态的切换，开销大——这就是 synchronized 早年被认为「重」的原因。

    锁升级（JDK 6 之后的优化）

    JDK 6 对 synchronized 做了大量优化，不再一上来就用重量级锁，而是随竞争激烈程度逐步升级，当前锁状态记录在对象头的 Mark Word 中：

    • 偏向锁：始终只有一个线程访问同步块时，第一次用 CAS 把线程 ID 写入 Mark Word，之后该线程再进入同步块只需比对线程 ID，几乎零开销。
    • 轻量级锁：出现第二个线程竞争时撤销偏向、升级为轻量级锁，线程通过 CAS + 自旋尝试把 Mark Word 指向自己栈中的锁记录，避免立刻阻塞。
    • 重量级锁：自旋若干次仍拿不到（竞争激烈），膨胀为重量级锁，抢不到锁的线程进入阻塞队列挂起，等锁释放后被唤醒。

    锁升级是单向的，只能升不能降。除锁升级外，JVM 还会做锁粗化（把相邻的多次加锁解锁合并为一次）和锁消除（JIT 逃逸分析证明锁对象不可能被其它线程访问时，直接去掉这次加锁）。

    [!amber]
    注意： 偏向锁的维护和批量撤销成本高、在现代应用中收益有限，JDK 15 起已默认禁用并标记为废弃（JEP 374）。面试聊锁升级时主动提这一点是加分项。

    synchronized vs ReentrantLock vs volatile

    synchronized vs ReentrantLock

    对比项 synchronized ReentrantLock
    实现层面 JVM 层面的关键字，基于监视器 JDK 类库，基于 AQS 实现
    加锁 / 释放 自动，代码块结束或抛异常都会释放 手动 lock()/unlock()，必须在 finally 中释放
    公平性 只有非公平 可选公平锁或非公平锁
    等待可中断 不支持 lockInterruptibly() 支持
    尝试获取 / 超时 不支持 tryLock() / tryLock(timeout)
    条件队列 一个监视器只有一个等待队列（wait/notify） 一把锁可建多个 Condition，能精确唤醒
    相同点 都是可重入的排他锁，都能保证原子性、可见性、有序性 同左

    选择建议：功能上 ReentrantLock 是超集，但 synchronized 写法简单、不会忘记释放锁，JDK 6 之后性能也已相差无几；只有在需要公平锁、可中断、超时、多条件队列这些高级特性时才有必要用 ReentrantLock。

    synchronized vs volatile

    • volatile 只保证可见性和有序性（禁止指令重排），不保证复合操作的原子性——i++ 是「读-改-写」三步，用 volatile 修饰依然会丢失更新；synchronized 三者都能保证。

    • volatile 只能修饰变量，不会引起线程阻塞，是更轻量的同步手段；synchronized 修饰方法和代码块，抢不到锁的线程会阻塞。

    • 二者典型的配合场景是双重检查锁（DCL）单例：synchronized 保证实例只创建一次，volatile 修饰 instance 字段禁止「分配内存 → 初始化 → 赋值引用」被重排序，防止其它线程拿到尚未初始化完成的对象。

    synchronized 关键字线程八锁

    这类题目的判断只有一条主线：看两个线程抢的是不是同一个监视器（monitor）。

    • 实例同步方法锁的是调用它的那个对象（this）；
    • 静态同步方法锁的是该类的 Class 对象（如 Something.class），跟通过哪个实例、哪个线程去调用无关；
    • 没加 synchronized 的方法不参与任何锁竞争。

    监视器相同就互斥，监视器不同（或有一方根本没加锁）就可以同时运行。下面习题中 x、y 是 Something 类的两个不同实例，允许同时运行画 ，否则画 。

    [!green-fold] 线程八锁结论

    • (1) 两个方法都没加锁，随便同时跑
    • (2) 同上，没加锁
    • (3) iA 没加锁，不参与竞争
    • (4) 都在抢 x 这一把对象锁
    • (5) 还是 x 这一把锁：一个对象的所有实例同步方法共用它
    • (6) x 的锁和 y 的锁是两把不同的锁
    • (7) 同上，两个实例两把锁
    • (8) cA 没加锁，不参与竞争
    • (9) x 的对象锁 vs Something.class 的类锁，互不干扰
    • (10) 都在抢 Something.class 这一把类锁
    • (11) 同上：一个类的所有静态同步方法共用类锁
    • (12) 通过实例调用静态同步方法，锁的仍是 Something.class，还是同一把类锁

    两个普通同步方法，两个 Number 对象，会同步吗？

    public class Test {
    public static void main(String[] args) {
        Number number1 = new Number();
        Number number2 = new Number();
        new Thread(() -> {
            number1.getOne();
        }).start();

        new Thread(() -> {
            number2.getTwo();
        }).start();
    }
}

class Number {
    public synchronized void getOne() {
        System.out.println("one");
        try {
            Thread.sleep(3000);
        } catch (InterruptedException e) {
        }
    }

    public synchronized void getTwo() {
        System.out.println("two");
    }
}

    [!green-fold] 参考答案
    不同步。两个线程分别锁 number1 和 number2，是两把不同的对象锁，"two" 立刻打印，不用等 3 秒。

        System.out.println("one");
        try {
            Thread.sleep(3000);
        } catch (InterruptedException e) {
        }
    }

    public synchronized void getTwo() {
        System.out.println("two");
    }
}

    [!green-fold] 参考答案
    不同步。getOne 锁 Number.class（类锁），getTwo 锁 number（对象锁），即使是同一个实例调用，两把锁也互不干扰。
